# Deployment

[中文](README.md)

The browser always requests `/api/v1` on the current origin. Caddy forwards API
requests to `backend:8080` and other requests to `frontend:3000`. The same
frontend image works with different domains without a build-time API URL.

## Local runtime

Run from the repository root:

```sh
docker compose up -d --build
```

Open `http://127.0.0.1:3000`. The same-origin health endpoint is
`http://127.0.0.1:3000/api/v1/health`. The development configuration also publishes
PostgreSQL, Go API, and security-kernel ports for debugging. Reuse the existing
Compose project name, such as `-p meta-org-ontology-final`, to keep using its
database volume.

For a local frontend, run `npm --prefix frontend run dev`. Its proxy defaults to
`http://127.0.0.1:8080`; set `API_PROXY_TARGET` to another HTTP(S) origin if needed.
Credentials, paths, queries, and fragments are rejected. The browser no longer
reads `NEXT_PUBLIC_API_URL`. Production `npm start` / standalone servers need
Caddy to forward API requests.

## Public HTTPS deployment

Provide Docker Compose, a domain pointing to the server, and publicly reachable
TCP ports 80/443. Caddy obtains and renews certificates automatically. UDP 443
enables HTTP/3. Only gateway ports are published in the production configuration.

Copy the environment template:

```sh
cp deploy/.env.production.example deploy/.env.production
```

Use `Copy-Item` in PowerShell. The real environment file is excluded by Git and
Docker build-context rules. Fill in all required settings; the template contains
no usable production secrets:

| Setting | Value |
| --- | --- |
| `APP_DOMAIN` | A hostname such as `app.company.com`, without a scheme, path, or port. |
| `ACME_EMAIL` | Email for certificate-related notices. |
| `POSTGRES_PASSWORD` | An independent random PostgreSQL password. |
| `PLATFORM_DATABASE_URL` | `postgres://postgres:<URL-encoded password>@postgres:5432/meta_org_saas?sslmode=disable`. |
| `TENANT_DATABASE_ADMIN_URL` | The administrative database on the same instance: `postgres://postgres:<URL-encoded password>@postgres:5432/postgres?sslmode=disable`. |
| `JWT_SECRET` | An independent random secret of at least 32 characters. |
| `MODEL_SECRET_KEY` | Exactly 32 bytes; back it up with the database because it decrypts stored provider and other credentials. |
| `SECURITY_KERNEL_SHARED_SECRET` | An independent random secret of at least 32 characters. |
| `META_ORG_PLATFORM_ADMIN_EMAIL` | Initial platform administrator email. |
| `META_ORG_PLATFORM_ADMIN_PASSWORD_HASH` | A bcrypt hash generated by `backend/cmd/bcrypt-hash`; enclose it in single quotes in the env file to preserve `$` characters. |

Run `openssl rand -hex 32` separately for JWT and kernel secrets, and
`openssl rand -hex 16` for a model encryption key containing 32 ASCII characters.
See the [root configuration guide](../README_EN.md#configuration) for the bcrypt
helper. Both database URLs must use the same PostgreSQL password; URL-reserved
characters in credentials must be encoded.

The application subnet defaults to `172.30.40.0/24`, with gateway IP
`172.30.40.2`. Other containers receive addresses from `172.30.40.128/25`, keeping
the fixed gateway address available. If the subnet conflicts with an existing
network, change `APP_NETWORK_SUBNET`, `APP_NETWORK_DYNAMIC_RANGE`, and
`PROXY_IP_ADDRESS` together. The dynamic range and gateway must be inside the
subnet, with the gateway outside the dynamic range. The backend trusts forwarded
client addresses only from that gateway
IP. This configuration assumes Caddy receives public traffic directly. Adding a
CDN or another proxy requires a corresponding client-IP trust configuration.

Validate and start from the repository root:

```sh
docker compose --env-file deploy/.env.production -f docker-compose.production.yml config --quiet
docker compose --env-file deploy/.env.production -f docker-compose.production.yml up -d --build --wait
```

This configuration uses the separate project name `meta-org-production` and its
own volumes. PostgreSQL first creates `meta_org_saas`, then the backend applies
platform migrations. The tenant provisioner creates `meta_org_xxxx` databases
and expands `tenantdb:include`; `xxxx` is the first four lowercase hexadecimal
characters of the organization UUID without hyphens. The tenant administrative
connection targets `postgres`, not the platform database.

Kernel readiness depends on the nonce table created by backend migrations, so
the backend starts once the kernel process has started. The public gateway still
waits for backend health, which includes kernel readiness.

Check health and open the login page:

```sh
curl --fail https://app.company.com/api/v1/health
docker compose --env-file deploy/.env.production -f docker-compose.production.yml ps
```

Health should report `ok` for the platform database and security kernel. Select
**SaaS management** and use the configured administrator account. Certificate
issuance requires working DNS, public ports, and access to the certificate
authority.

## Updates and retained data

After updating the code, repeat the start command with the same env file, Compose
file, and project name. The backend applies validated migrations at startup.
Back up the platform database, each tenant database, and encryption keys before
upgrades. `pgdata` stores database files; `caddy_data` / `caddy_config` retain
certificates and Caddy state. Normal container updates reuse these volumes.

## Gateway checks

These checks use isolated HTTP fixtures and do not connect to application data:

```sh
docker compose -f deploy/tests/docker-compose.yml up --abort-on-container-exit --exit-code-from checks
docker compose -f deploy/tests/docker-compose.yml down
```

They cover page/API routing, query strings, authentication and organization
headers, forged client-IP headers, uploads, downloads, upstream errors, the first
SSE event, and cancellation when the client disconnects. CI also validates the
production Compose/Caddy configuration and runs browser tests through the
development server's same-origin API proxy.

With Node.js 20.9+ installed, run the complete fresh-installation check:

```sh
node deploy/tests/production-smoke.mjs
```

It builds the current code and starts the production configuration in a separate
project with temporary databases. HTTPS, platform login, and tenant provisioning
are checked on loopback ports 18080/18443 using a temporary `localhost`
certificate, without requesting a public certificate. Its containers, volumes,
and temporary build images are removed afterward. To reuse existing images, set
all three variables: `DEPLOY_TEST_FRONTEND_IMAGE`, `DEPLOY_TEST_BACKEND_IMAGE`,
and `DEPLOY_TEST_KERNEL_IMAGE`. Reused images are retained.

For a 502 at `/api/v1/health`, inspect backend health and gateway logs. For a
frontend 404, check that the entry point is Caddy or the Next.js development
server, rather than a production frontend port without an API proxy.
